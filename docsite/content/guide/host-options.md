## `Bind`, `Budget` and the context

```go
{{ includeFileText "examples/guide/options_test.go" }}
```

`Bind` gives a goal variable its value from Go, so the query text stays fixed and nobody builds queries out of strings. A bound variable behaves as if its value were written into the goal, and that includes counting as the anchor of a `not` (see [negation]({{.Site.PathPrefix}}/guide/negation/#a-not-has-to-be-anchored)). The answer still has the bound column, filled with the value. Binding a variable the goal doesn't use is an error, since it's pretty much always a typo, and a typo there would otherwise answer the unbound question without a word.

A variable can be bound to several values too, which is how a host asks one question about a whole selection, such as every package a user ticked. The variable then ranges over the values, as if the goal were joined with a relation holding exactly them, so the answer is the union, and an aggregate like `count(distinct ?d)` counts across the whole set, which asking once per value can't do. Demand starts from every value, so a recursive relation is still worked out only for the values asked, and one query costs about what the separate ones would. Each value is checked as a single one is, and an error names the one refused. A variable bound to no values matches nothing: the answer is empty, or the one row an aggregate gives over nothing (a count of 0). A set of one value is the same as binding that value.

`Budget` caps the work one `Eval` does, counted the same way on every run, so a budget that passes once passes every time. `Base.Work` reports what a query used, which is how to size a budget from your real queries. It bounds work, not memory. What a query holds grows with its answer rather than its work: a goal keeps one row per distinct answer, or one running total per group for an aggregate, not every combination it found on the way ([#120](https://github.com/panyam/jaala/issues/120)), so a count over a million bindings holds one group. The derived relations a query's rules produce are held in full, though, and those do grow with the work. So is a relation the source hands over as one slice: it's all in memory before the budget sees any of it. A source that implements `ns.StreamSource` hands a relation over one fact at a time instead, and each fact counts against the `Budget` as it arrives, so a query over a relation bigger than its budget stops having held at most that many facts ([#233](https://github.com/panyam/jaala/issues/233)). Those facts aren't work: `Base.Work` and `Explain` count what the query did with them, and only the budget, and the `BudgetExceeded` it stops with, adds the read. A read the budget stopped isn't kept, so the next query reads the relation again. A `Federation` streams its members in turn, so it stops before the next member's read even when its members return slices. When the goal is the only reader of a streamed relation (no rule reads it, and the goal reads it once, first), its facts go straight into the answer as they arrive and aren't kept ([#264](https://github.com/panyam/jaala/issues/264)): a `limit` without an `order by` stops the read at its rows, and a count holds its one group rather than the relation. The next query that needs the relation reads it again, unless something else already kept it. A relation the source can look up streams this way only under such a `limit`, so a repeated question over it still asks the source nothing.

The context reaches every `Eval`. When it's cancelled or its deadline passes, the `Eval` stops at its next check, which comes every 1024 units of work, and returns an error that wraps the context's own, so `errors.Is(err, context.DeadlineExceeded)` works. It also reaches a host's own Go code running inside a query, its generators and sources, so those can stop too.

## Pages, totals and tables

`After`, `Total` and `EvalTable` are for a host showing a big answer a page at a time, such as a viewer listing everything on a net ([#194](https://github.com/panyam/jaala/issues/194), [#195](https://github.com/panyam/jaala/issues/195)). `Example_page` and `Example_table` in the code block above show them.

`After` takes the last row of the page before, as the host got it, and answers only what comes after it in the query's `order by`, as the query's own `after` clause would ([ordering]({{.Site.PathPrefix}}/guide/ordering/#paging-with-after)). With a `limit`, each page holds only its own rows while it runs, and a page stays put when the facts change between requests. `Total` fills an `int` with the number of rows the whole answer has before `after`, `offset` and `limit`, so the page can say how many it left out. Counting needs the whole answer, so a `limit` without an `order by` doesn't stop early when `Total` is asked for.

`EvalTable` returns the same answer as `Eval`, as a `Table` of columns and rows of values, with each row's citations, witness and reasons beside it. `Eval` gives every row a map of its own, which for a small row costs several times its values, so a host serializing a large answer is better off with the table. `Table.Row(i)` is row `i` as `Eval` returns it. `Explain`'s `Report.Held` says how many rows (or groups) the goal held at its peak.

## Explaining a slow query

`Explain` fills a `Report` with what an `Eval` did, so a slow query shows where its work went rather than one total to bisect by hand ([#147](https://github.com/panyam/jaala/issues/147)). `Example_explain` in the code block above prints part of it. `Report.String` prints all of it, and the struct has JSON tags, so a host can log it beside a slow query or return it with an answer.

The report lists each derived relation the query reached, and whether it was evaluated in full, under demand (with how many values were demanded), as a factored walk, inlined into its callers, or reused from what the `Base` kept from an earlier query. Each comes with its tuples, rounds and work.

It then shows the goal and each rule body in the order it actually ran, after jaala's rewrites, labelled with the rule as you wrote it. Every literal says how it was read (an index on which arguments, a scan, a generator or a filter), how often solving reached it, how many bindings it passed on, and how many candidates it examined. A literal reached thousands of times is usually the place to look.

Last come the base relations it read, whether the `Base` already held them, and the indexes it probed, with whether this `Eval` built them. For a source that looks facts up (below), each relation also says how many lookups it took, the tuples they fetched, and how many calls were answered again from what an earlier lookup in the same `Eval` returned. `Report.Fetched` totals the tuples the source handed this `Eval`, and `Report.Lookups` the calls.

`Work` is what the `Eval` spent, which is what a `Budget` caps, so it depends on what ran on the `Base` before: a query reusing a relation an earlier one kept costs less. `Report.Cold` is the same query's cost on a base that kept nothing, which doesn't move from run to run, so it's the number to compare two queries or plans by, or to suggest a budget from. When the query reused something, `Explain` finds it by running the query again on a copy of the base that keeps nothing. That run doesn't count toward `Base.Work`, but it does read the source again.

The report is filled even when the `Eval` fails, so a query its `Budget` stopped still shows what spent the budget. Asking for it costs time in proportion to the rules and literals a query runs. Not asking costs nothing measurable, which is why it's off by default.

## Sharing a base

A `Base` pairs a vocabulary with one source's facts, and caches and indexes what it reads. It's safe to share between `Eval`s running at the same time, since each `Eval` keeps its own state. Build one per dataset, and reuse it for every query over that dataset, which mostly comes free once the vocabulary is built at startup.

It also keeps the derived relations a query evaluated in full, so the next query calling the same relation reads it instead of deriving it again ([#140](https://github.com/panyam/jaala/issues/140)). A library member that three workbook tabs all call is derived once. The key is the relation's rules and everything they read, so a query that sends its own definition of a relation derives its own. A relation derived only for the values one query asked about isn't kept, since it's partial. Only `SemiNaive` uses the cache, and not under `Witnesses`. `Base.LimitDerivedCache` sets how many derived tuples the base keeps (about a million by default, and 0 turns it off), dropping the relations used least recently first.

A base's memory lasts as long as the base. A host that builds a base per request, runs several processes, or wants its own tools to read what a rule derives can also give the base a store with `Base.KeepDerivedIn` ([#220](https://github.com/panyam/jaala/issues/220)). The store implements `ns.DerivedStore`, two calls: `Derived` hands back a relation it holds, and `KeepDerived` takes one a query evaluated in full. Each relation is filed under an `ns.DerivedKey`: its name, the text of its rules and everything they read (the same key the base's memory uses), and the source's `Version`. A second base over the same version then reads the relation from the store instead of deriving it, which is what a federation of stores wants when the same rules run against the same members again. The store is read when the base's memory misses, so `LimitDerivedCache(0)` leaves it as the only tier. Only a `Versioned` source's relations go there, since an unversioned source's facts have nothing to file them under, and the same evaluators and options use it as use the memory. A store that fails, or hands back tuples of the wrong arity, costs the work of deriving and never changes an answer. `SemiNaive.Materialize` derives the relations you name in full and keeps them, with everything they read, ahead of any query, and returns the store's error if it refused one. It also keeps a relation with one rule, which a query would have folded into its caller rather than derived. `ns.MemDerivedStore` is one held in memory, and its `Relation(rel, version)` reads a kept relation back as facts.

All of this assumes the source's facts don't change while the base is kept. If yours can, have the source implement `ns.Versioned`, whose `Version` string changes whenever the facts do. Each `Eval` reads it first, and when it has moved, the base drops everything it cached and reads the source again. A host that changes facts in place without a version calls `Base.Forget` instead. A generator whose answers can change while the facts don't (one reading the clock, say) sets `Volatile` on its `ns.Builtin`, and no relation reading it is kept.

## A source with its own index

A source reads a relation whole: the first query touching `pin` loads every `pin` fact into the base. A source backed by a database or an on-disk index can do better by implementing `ns.LookupSource` ([#126](https://github.com/panyam/jaala/issues/126)). Then a call with an argument bound, such as `pin(?r, "GND")`, or one that demand bound for a derived relation's body, asks the source's `Lookup` for just the facts it needs. Lookup gets the bound positions and their values. It may return facts that don't match, since the engine checks each one, but it must not leave out one that does. A bound value arrives already read as its argument's declared type, and a stored value matches when, read as that type too, it's the same value: two numbers by value however they're spelled, two texts by their text, and a number never text. jaala reads what Lookup returns that way, so a pin stored as the number 3 matches a bound `"3"` in a pin column. A source whose stored kinds already match its declared types can compare as stored.

What a lookup returns is kept for the rest of the `Eval` that asked, and by the `Base` for later queries, up to a million tuples across all lookups by default ([#212](https://github.com/panyam/jaala/issues/212)). A host that keeps a base open and asks the same kinds of question again goes back to the store only for what it hasn't asked before. When the cache is full, the results used least recently go first, so a relation the queries only probe is held only as far as it was probed and never past the limit. `LimitLookupCache(n)` sets the limit for a base and every copy of it, and `LimitLookupCache(0)` keeps nothing, so every query asks the source again. A `Versioned` source whose version moves drops what was kept, as `Forget` does, and `Explain` counts a call answered this way as kept, apart from the query's own hits. A call with nothing bound still reads the relation whole, and the base then keeps it and answers later bound calls from its own index. Each lookup counts one unit of work against the `Budget`, and a failed one stops the query with an error naming the relation and isn't kept. `Unindexed` never looks anything up, so it stays the oracle a host compares against. Since the planner can't size a relation it hasn't read, it orders those calls by how many arguments they bind.

## Facts in several stores

A host whose facts live in several stores, say one per repo or a project's own facts beside a shared parts library, doesn't have to merge them into one source first. `ns.NewFederation` builds one source over several members ([#211](https://github.com/panyam/jaala/issues/211)). Each relation's facts are the union of what its members serve, and a relation two members serve must have the same arity, labels and types in both, or `NewFederation` refuses it.

A member's `Holds` says which calls it can match. `ns.HoldsPrefix("github.com/acme/api/", map[string][]int{"node": {0}})` says every `node` id the member stores starts with that prefix, so a lookup of `node("github.com/acme/web/main.go", ?k)` skips it. Binding fewer arguments must never answer false where binding more would answer true, since a federation may ask about a relation with nothing bound before it tries each value ([#307](https://github.com/panyam/jaala/issues/307)). A lookup goes only to the members that can hold a match, which makes a query asking about one repo cost one store's round trip, not fifty. A relation is looked up only when every member serving it answers lookups; otherwise it's read whole from every member, once, and kept like any other relation read whole. A member's `Name`, when set, prefixes its facts' citations (`api:main.go:12`), so an explanation says which store each fact came from. The federation's version moves whenever a member's does. A fact two members both serve is two facts, as it would be in one source serving it twice: answer rows are distinct either way, but an aggregate counting bindings counts it twice.

A source can also say which lookups it answers from an index by implementing `ns.IndexedLookups` ([#154](https://github.com/panyam/jaala/issues/154)): `Indexed(rel, bound)` reports whether a lookup of `rel` with those positions bound reads an index. The planner can't size a relation it hasn't read, so it orders looked-up calls by how many arguments they bind, and a call the source would scan ranks as if it bound nothing. In `attr(?m, "lines", "7"), edge("repo0/n3", _, ?m)`, with `attr` indexed only by its id, the planner reads `edge` by its source first and then looks up `attr` by each `?m`, where it would otherwise scan every `attr` for the key and value. A source that doesn't implement it is taken as indexing everything. A federation indexes a pattern only when every member serving the relation does, since one member's scan makes the call a scan.

Under demand, a body probes a looked-up relation once for each value it's given, so a question reaching 500 nets makes 500 calls, each a round trip when the store sits behind a worker or a network. A source that implements `ns.BatchLookupSource` ([#153](https://github.com/panyam/jaala/issues/153)) is asked for all of them at once instead: `LookupBatch(ctx, rel, positions, values)` gets the bound positions and a list of values, and returns one result per value, in that order, each under `Lookup`'s rules. The planned `SemiNaive` finds the values by running the body up to the call, asks for the ones it hasn't looked up in batches of up to 1024, and then solves the body from what came back, so `reach("repo0/n0", ?x)` costs one call per level of the walk rather than one per node. A negated call, `not attr(?x, "v0")`, gets its values from one more run of the whole positive body ([#230](https://github.com/panyam/jaala/issues/230)). One call per level of a walk is as far as batching goes, since each level's values come from the level before; a store that walks the graph itself is pushdown ([#213](https://github.com/panyam/jaala/issues/213)). The extra run of the body works in memory. A federation batches whatever its members are, asking each member once for the values its `Holds` allows, and a member that only looks up is asked one value at a time. `Explain` counts batches apart from lookups (`Report.Batches`).

## A store that joins

A store that can evaluate a join, such as SQLite turning a conjunction into one statement, can implement `ns.PushSource` ([#237](https://github.com/panyam/jaala/issues/237)). The planned `SemiNaive` then hands it a group of a body's base literals joined by shared variables, with the comparisons and filter predicates over them, and solves the rest itself. `edge("repo0/n5", _, ?m), edge(?m, _, ?o)` becomes one call that ships the rows that join, where lookups would cost a call per literal and ship every intermediate tuple. A single literal goes too when the store can filter it and nothing else would ([#263](https://github.com/panyam/jaala/issues/263)): `edge(?a, ?k, ?a)` repeats a variable, and `weight(?n, ?w), ?w > 7` has a comparison the store takes, so each ships its matches instead of the whole relation. A literal with a constant is still a lookup, and one of distinct free variables is read whole. `Pushes(c)` says whether the store takes a conjunction. The planner asks it while planning, growing a group one literal at a time and offering it with its comparisons and filters, then without the filters, then without either, so it has to be cheap and do no I/O. A filter predicate such as `str.glob(?c, "net/http.*")` goes as `Conjunction.Filter` when the store names it in `ns.FilterSource` ([#297](https://github.com/panyam/jaala/issues/297)), which it does only when it applies the predicate exactly as the vocabulary does; `str.glob` has SQLite GLOB's semantics, so a SQLite store can apply it as `GLOB`. A store that names none is sent none, since one that accepted a conjunction and ignored a filter it didn't know would join every row the filter drops. A group stops growing at a literal outside it that only filters what it bound, such as a derived relation over one of its variables, or a filter predicate the store refused, so the store isn't asked to join rows the filter would drop ([#291](https://github.com/panyam/jaala/issues/291)). `Push(ctx, c)` streams one row per combination of facts that satisfies the conjunction, each row one tuple per atom in the order asked.

A row follows `Lookup`'s rules: the engine reads each tuple as its argument's declared type and checks it against the literals, the comparisons and the filters again, so a row that doesn't satisfy them is dropped, but one that does must not be left out. A store that can't compare as jaala does (absent first, then numbers by value, then text, with a number in no unit comparing with any unit) skips that comparison and leaves it to the engine, and likewise any filter. A group may also read variables something earlier in the body binds, such as a demanded rule's guard or a recursive round's delta ([#246](https://github.com/panyam/jaala/issues/246)): the planner offers it with those variables as `Conjunction.Inputs`, and a store that takes them is later asked once for a batch of bindings (`Conjunction.Bindings`), returning every match for each, as `LookupBatch` does for one literal. A store that declines is asked literal by literal, with its lookups batched as before, never a push per binding. A partitioned federation of several members takes inputs when every member does ([#268](https://github.com/panyam/jaala/issues/268)): each binding goes to the members whose `Holds` allows the group's first literal under its values, each of them asked once for its own bindings, and an unpartitioned one declines. Where a match leaves one member, the rest of the group goes to the others once for every such prefix, with the prefixes' values as its bindings, rather than once per prefix. A federation of any kind pushes a single literal to each member serving it. Each row is charged to the `Budget` as it arrives. A completed push is kept like a lookup's result, and one that failed or stopped isn't. A federation of one member pushes what that member pushes. `Explain` shows a pushed group as one literal, `pushed{edge("repo0/n5", _, ?m), edge(?m, _, ?o)}`, and counts the calls in `Report.Pushes`.

Across several stores a join can pair facts from different stores, which no one store sees. A federation built with `ns.NewPartitionedFederation` pushes anyway ([#238](https://github.com/panyam/jaala/issues/238)). It sends the conjunction to each member whose `Holds` allows its first literal, asking for every prefix of its matches too (`Conjunction.Partial`), so a member answers the matches it holds whole and also says where each one stopped. A prefix whose next fact another member's `Holds` allows is continued there, with the prefix's values as constants. With stores partitioned by repo, `edge("repo0/n20", _, ?m), edge(?m, _, ?o)` costs one call to repo0, and one to repo1 for the edge that leads there, where asking literal by literal costs three. The answer doesn't depend on how precisely `Holds` routes, since a prefix is continued in every other member `Holds` allows, so a loose `Holds` costs calls rather than matches. The federation pushes only when every member serves every relation of the conjunction and pushes it with its prefixes; otherwise it's asked literal by literal. A store asked for prefixes must return them, or the matches spanning stores are lost, so a store that can't refuses a `Partial` conjunction in `Pushes`. A member is asked for prefixes only when another member's `Holds` allows a literal after the first; otherwise it gets the conjunction whole, without `Partial`. A conjunction with a literal no member's `Holds` allows is answered with nothing, and no store is asked ([#307](https://github.com/panyam/jaala/issues/307)). One that pushes a conjunction also pushes its suffixes with some variables given as constants.

## A store that counts and pages

A goal whose whole body a store could evaluate goes to it whole ([#240](https://github.com/panyam/jaala/issues/240), [#241](https://github.com/panyam/jaala/issues/241)): base relations it serves, and comparisons over their variables, with no negation and no derived relation. Over a federation that means a goal of one literal, whose matches are each one store's facts, or any goal over one store, or a join over a partitioned federation ([#253](https://github.com/panyam/jaala/issues/253)). There each store summarizes or pages the matches it holds whole, and also sends only the prefixes of its matches (`Conjunction.PrefixesOnly`), which the federation continues in the stores holding the next fact, as a partitioned push does. Each match spanning stores comes back as a summary row of one match, or as a candidate for the page, so every match is counted once. A join's summary across stores asks for values, not extremes, since the federation can't read a crossing match's numbers as their types.

A goal that aggregates, `attr(?id, "lines", "7") => count(?id)`, asks a store implementing `ns.SummarySource` for a summary: `Summarize(ctx, c, ns.Summary{Group, Values})` returns the matches grouped by the values of the group's variables and of the variables the aggregates reduce, each row with how many matches it covers and their citations. A plain `count` reduces no values, so it is one row per store. jaala reduces the rows with its own aggregator, so sums stay exact, numbers in mixed units answer absent, `list` repeats a value as often as it occurred, and `Row.Why` says why. Two matches share a row only when their values are identical in text, number and unit, since 5 V and 5 A are one number in two units; a store may split rows it could have merged, but must count every match once. A store may skip the goal's comparisons, since jaala asks for the values they read and checks each row.

A variable only `min` and `max` read goes as one of the summary's `Extremes` ([#252](https://github.com/panyam/jaala/issues/252)): rather than group by its values, a row reports, per unit, how many of its matches hold a number there, whether one was NaN, and the smallest and largest of the rest (`ns.Extreme`). A `max` over a column of distinct measurements is then a row per group rather than one per value. jaala still decides the answer: numbers in different units answer absent, and a NaN makes it NaN. A store that can't report extremes refuses a summary with them in `Summarizes`, and is asked for the values instead. `sum` always goes as values, since an exact sum isn't something a store's `SUM` gives.

A goal with a `limit` sets `Conjunction.Page`: the answer's columns, the `order by` keys and `limit` plus `offset`. The store returns every match behind its first that many distinct rows in jaala's order (absent, then numbers by value, then text), and jaala answers from them as from every match, so the rows, the binding each row cites and its witness are the same. Each store's first rows hold the federation's, so a page of 10 over 50 stores ships at most 10 rows from each. A page after a cursor, from the `After` option or the query's `after` clause, carries the cursor's values in `Page.After` ([#254](https://github.com/panyam/jaala/issues/254)), and the store takes its first rows after them in the same order, so every page of a listing ships its limit per store. jaala applies the cursor again, so a store that sends rows from before it costs shipping, not answers. A goal with a comparison, or a `Total` asked for, isn't paged.

## A store that walks

A recursive rule that follows a relation, as `walk(?a, ?c) :- walk(?a, ?b), next(?b, ?c)` follows `next`, probes it in rounds: each round looks up the values the last round found, so a walk 60 steps deep costs 60 calls however the lookups batch. A store that can follow a relation itself, as SQLite does with `WITH RECURSIVE`, can implement `ns.WalkSource` ([#239](https://github.com/panyam/jaala/issues/239)). The planned `SemiNaive` then asks it once, `Walk(ctx, ns.Walk{Relation: "next", From: 0, To: 1, Start: [n0]})`, and the store returns every `next` fact it reaches from n0 by following each fact's `dst` as the next `src`. jaala files each reached value's facts as the lookup that value would have made, a value with no facts as an empty answer, and runs its fixpoint as before, so answers, citations and witnesses don't change, only the calls.

A walk follows `Lookup`'s rules. The store may return facts that aren't reached, but for a value it reaches it must return every fact, since jaala asks nothing more about that value. jaala files only the values it reaches itself from the start values, so a stray fact never stands in for a value's whole answer. A walk may fix other arguments to constants (`edge(?b, "calls", ?c)` walks only calls), and is charged to the `Budget` fact by fact. A completed walk is kept as lookups are; one that failed or stopped isn't, and its error reads as a failed lookup. A probe a walk didn't cover, such as a value the recursion reached through another relation, is looked up as before, or walked again from there.

A federation walks across its members whatever `Holds` says: each start value goes to the members `Holds` allows, each member walks its values in one call, and a value it reached goes on to the other members `Holds` allows, each member walking a value once. A walk that stays in one repo costs one call, and one crossing into another repo a call per store. `Explain` counts walks in `Report.Walks` and shows the literal as `walked (src)`.

A recursive rule whose step is several literals, `r(?a, ?c) :- r(?a, ?b), edge(?b, ?m), call(?m, ?c)`, walks a conjunction rather than a relation ([#250](https://github.com/panyam/jaala/issues/250)). A store implementing `ns.ConjunctionWalkSource` is asked once, `WalkConjunction(ctx, c, in, out, start)`, for every match of the step from the start values, following each match's `out` value as the next `in`, and jaala files each reached value's matches as the batched push (#246) of that value would have. It walks only a step the planner keeps as one pushed group: when the demand rewrite stores part of the step in a prefix relation (a literal bound by constants, such as a kind filter, is often split off that way), the rounds go to batched pushes instead. A federation walks a step only through a lone member.
